## Текущие наблюдения и их уровень зрелости

**[L1] Classification Failure — гипотеза, не факт.**
Наблюдение из проекта репетитора: первая ошибка = неправильная классификация системы. «репетитор» → учитель → урок → Learning Engine → цепочка пошла не туда.
Гипотеза: это корень всех остальных дефектов, глубже чем Premature Commitment.
Проверка: нужны три разных следующих проекта. Если во всех первой ошибкой окажется неправильная классификация — L2.

**[L1] Pipeline как граф с точками возврата.**
Наблюдение: при ошибке нужно возвращаться в конкретную точку, не к началу. Точки возврата: Classification failure → Classify | Unknown SoT → Source of Truth | Architecture failure → Hypothesis (не Architecture).
Проверка: нужна практика на реальных проектах.

**[L1] Claude OS структура.**
Наблюдение: единый bootstrap-файл смешивает сущности с разным жизненным циклом.
Гипотеза: разделение вход + ядро + pipeline + platform + memory — правильное разделение. Ядро меняется редко. Pipeline чаще. Platform по версиям Claude. Memory постоянно.
Проверка: реализовывать только после L3 по паттернам, которые туда войдут.

**[L1] Solution Escalation как Defect 0.**
Наблюдение: хорошая идея → новый документ → изменение архитектуры за один шаг. Проявился прямо в исходной сессии.
Корень: нет системы уровней зрелости. Любое наблюдение казалось готовым к внедрению.

## Три симптома Premature Commitment

Все три — следствия одной корневой причины, не самостоятельные дефекты. Устраняются через Meta Heuristics ниже.

- **Преждевременная конкретизация** — строю решение до того как понял задачу. Лечится Meta #1.
- **Этажная ошибка** — проектирую компонент (учитель, хранилище данных) вместо системы. Лечится Meta #2.
- **Complexity drift** — вижу идеальную систему → требую полную реализацию, минуя MVP. Лечится Meta #3.

## Meta Heuristics — как думать (до и во время проектирования)

Применяются первыми. Если не пройдены — Design Heuristics задаются про неправильную задачу.

**Meta #1 — «Какую задачу я на самом деле решаю?»** До любого решения: что стоит за словами заказчика? Как проверил, что именно эту задачу он поставил? *Предотвращает: Premature Commitment.*

**Meta #2 — «На каком этаже?»** Перед каждым ответом: я проектирую компонент или систему? Если компонент — есть ли согласованная модель системы выше? *Предотвращает: этажную ошибку.*

**Meta #3 — «Самая простая версия сегодня.»** Перед финальной архитектурой: как запустить с тем, что есть? Если ответ требует двух недель — переусложнено. *Предотвращает: Complexity drift.*

---

## Design Heuristics — что проектировать (внутри архитектуры)

**Design #1 — «Данные или модель?»** Храню что произошло или что это означает? Интерпретация ценнее сырых событий. *Предотвращает: хранение фактов без диагноза.*

**Design #2 — «Чья это цель?»** Цель исходит из системы или из пользователя? Система не преследует собственных целей. *Предотвращает: подмену цели пользователя целью компонента.*

**Design #3 — «Кто не должен это касаться?»** Кто из участников не должен оперировать руками? Трение для пользователя = ошибка дизайна. *Предотвращает: перекладывание системной работы на пользователя.*

## Обязательный ритуал перед «архитектура готова»

Gate, не рекомендация. Без ответов на все — архитектура не готова.

0. Какую задачу я на самом деле решаю? Как проверил, что именно эту задачу поставил заказчик? → Meta #1
1. Что является Source of Truth? (их может быть несколько)
2. Что является состоянием системы? (не данные — модель) → Design #1
3. Где проходит граница полномочий AI? → Design #2 + #3
4. Какую самую простую версию можно запустить уже сегодня? → Meta #3
