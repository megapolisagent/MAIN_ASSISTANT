## 1. Цель проекта

Агентство недвижимости Мегаполис (Мария — единственный сотрудник сейчас, будет расти). Регулярный процесс: сделка (аренда или продажа объекта), по ней нужен комплект документов — договоры комиссии с каждым участником сделки, основной договор со всеми сторонами, акты приёма-передачи, согласия. Сейчас документы собираются вручную из разрозненных шаблонов, накопившихся без единого правила, какой брать.

**Срочная цель:** рабочий инструмент под текущую сделку, с удобным экраном ввода, не через файлы кода.
**Стратегическая цель:** заложить структуру данных так, чтобы её не пришлось переделывать при росте в агентство и, позже, при упаковке в продукт для других агентств.

## 3. Классификация (Classification Gate)

**Что является системой:** генератор документов — динамическая структура входных данных (Сделка + список участников) + правила состава комплекта + реестр шаблонов с плейсхолдерами + движок подстановки. Регулярный, повторяющийся процесс с чёткими входами и выходами, число участников и документов заранее не фиксировано.

**Что не является системой:** содержание шаблонов (юридический текст) — решает Мария/юрист, не автоматизация. Правила, когда именно нужно согласие супруга/органов опеки/содольщика — решает юрист, система только исполняет уже определённое правило. Нетиповые сделки — система готовит черновик, финальную формулировку определяет человек.

**Что может изменить классификацию:** переход от «инструмент для себя» к «продукт для других агентств» — тогда добавляются мультитенантность, биллинг, требования 152-ФЗ на уровне продукта. Это Phase 3, не текущее ТЗ.

## 4. Структура входных данных — Сделка (Deal)

Ключевое изменение v1.1: стороны — не два фиксированных поля, а **динамический список участников**. В реальной сделке может быть несколько собственников (доли) и несколько покупателей/арендаторов.

```
Deal
├── deal_id, deal_type (аренда | продажа), status, created_at, agent_id
├── Object (объект недвижимости)
│   ├── address, cadastral_number — кадастровый номер (номер объекта в гос. реестре)
│   ├── property_type, area, rooms
│   ├── ownership_basis — документ основания права собственности
│   └── encumbrances — обременения, если есть
├── Participants — список участников (1..N), не фиксированная пара
│   └── каждый Participant:
│       ├── participant_id
│       ├── side — «сторона объекта» (арендодатель / продавец) | «сторона контрагента» (арендатор / покупатель)
│       ├── full_name, passport_data, registration_address, contact
│       ├── representative — данные доверенности, если действует не сам
│       ├── ownership_share — доля в праве собственности (для стороны объекта, если долевая)
│       └── consent_flags — is_married (в браке), is_minor (несовершеннолетний), has_other_co_owners (есть содольщики вне сделки) — определяют потребность в согласиях, см. раздел 5
├── Deal Terms
│   ├── price, payment_schedule
│   ├── deposit — залог (аренда) / задаток-аванс (продажа)
│   ├── term — срок аренды или дата передачи объекта
│   └── special_conditions
└── Commission Terms
    ├── commission_per_participant — % или сумма, срок оплаты, может отличаться по участнику
    └── agency_details — юр. данные агентства (название, ИНН, ОГРН, подписант)
```

Одна структура Deal обслуживает и аренду, и продажу — разница в наборе активных полей и в правилах состава комплекта (раздел 5).

**consent_flags — ПРЕДПОЛАГАЮ**, что именно эти три признака определяют потребность в согласиях (супруг, опека, содольщики) — точный список оснований и условий, когда согласие обязательно, **[УТОЧНИТЬ]** у юриста. Система хранит флаги и правило как настраиваемые данные, не зашивает конкретный юридический список в код.

## 5. Логика генерации динамического комплекта

### Состав комплекта — не фиксированные 3 документа

Число документов в комплекте (типично 5–10) зависит от числа участников:

| Тип документа | Сколько штук |
|---|---|
| Договор комиссии | 1 на каждого участника (и сторону объекта, и сторону контрагента) |
| Основной договор (аренды / купли-продажи) | 1, перечисляет всех участников обеих сторон |
| Акт приёма-передачи | 1 на сделку (ПРЕДПОЛАГАЮ — типовая практика; **[УТОЧНИТЬ]**, если нужен акт на каждого участника отдельно) |
| Согласие (супруга / опеки / содольщика) | 0..N — по одному на каждого участника, у кого выставлен соответствующий `consent_flag` |

Пример на 2 собственников (в долях) + 1 покупатель, один из собственников в браке: 3 комиссии + 1 основной договор + 1 акт + 1 согласие супруга = 6 документов.

### Реестр шаблонов (Template Registry)

Каждый шаблон: `document_type` (комиссия | основной_договор | акт_приема_передачи | согласие) × `deal_type` (аренда | продажа) × `version` × `status` (draft | active | archived).

**Правило, снимающее исходную проблему («шаблоны накопились без единого правила»):** на пару (document_type × deal_type) может быть только один шаблон со статусом `active`. Новая версия проходит `draft` → подтверждение Марией → `active`, старая уходит в `archived`, не удаляется.

### Поток генерации

1. Пользователь вводит объект, добавляет участников по одному (кнопка «добавить участника»), заполняет условия сделки.
2. Система по правилам раздела 5 определяет итоговый список документов под конкретный состав участников.
3. Проверка полноты данных под этот список — если чего-то не хватает, генерация блокируется, показывается список недостающих полей по каждому документу.
4. Генератор рендерит каждый документ из активного шаблона нужного типа, подставляя данные конкретного участника (для комиссии и согласия) или всех участников сразу (для основного договора и акта).
5. Автосверка комплекта: цена/адрес/ФИО идентичны во всех документах комплекта, где встречаются — расхождение возможно только при ошибке маппинга.
6. Комплект сохраняется как Package с привязкой к точным версиям использованных шаблонов.
7. Экспорт — набор файлов .docx с понятными именами (например, «Комиссия — Иванов ИИ.docx», «Основной договор.docx», «Согласие супруга — Петрова ИП.docx»), чтобы не путать файлы при 5–10 штуках в комплекте.

### 5.1 Особые условия — гибрид «шаблон + свободный ввод» (Phase 1.2, добавлено v1.2)

Три уровня гибкости для нестандартных условий сделки:

1. **Базовый шаблон** — юридический каркас документа, не меняется (раздел 5, Template Registry).
2. **Библиотека переключателей** — типовые особые условия (животные в квартире, рассрочка комиссии, субаренда и т.п.). Архитектурно — это просто маленькие шаблоны-фрагменты (snippet-шаблоны), они хранятся и версионируются в том же Template Registry, что и основные документы, отдельного механизма не требуется.
3. **Свободный ввод + AI** — поле «опиши условие своими словами», AI переформулирует в юридический пункт.

**Обязательное правило для уровня 3 (рекомендация ассистента, ждёт подтверждения владельца):** AI-сформулированный пункт **не встраивается в файл автоматически**. Поток: AI предлагает формулировку → показывается на экране 3 для подтверждения/правки → только после подтверждения пункт попадает в .docx. Причина — это единственное место в документе, где текст не проверен заранее (в отличие от шаблонов, которые Мария/юрист утвердили один раз и переиспользуют), и именно на нестандартных пунктах рыночное исследование (`ENGINEER\workspace\agent-runs\2026-08-21-legaltech-market-research.md`, раздел 12 источников) отмечает, что AI даёт «сильный первый черновик», но требует проверки человеком.

## 6. Интерфейс (UI) — требования к экранам

Мария явно попросила визуальный интерфейс (веб-форма), не работу с файлами кода через терминал.

**Экран 1 — Новая сделка.** Выбор типа сделки (аренда/продажа), форма объекта (адрес, кадастровый номер, площадь и т.п.).

**Экран 2 — Участники.** Список участников с кнопкой «добавить участника»; на каждого — форма (ФИО, паспортные данные, роль — сторона объекта/сторона контрагента, доля, флаги брак/несовершеннолетний/содольщики). Можно добавлять и удалять участников до генерации.

**Экран 3 — Условия сделки.** Цена, порядок расчётов, срок, комиссия по каждому участнику. Особые условия (Phase 1.2, раздел 5.1): чекбоксы для типовых ситуаций + поле свободного текста → предложенная AI формулировка показывается на этом же экране для подтверждения/правки перед тем, как попасть в итоговый файл.

**Экран 1.1 — Загрузка документов (Phase 1.1, добавлено v1.2).** Зона загрузки фото/скана паспорта каждого участника и выписки ЕГРН. После загрузки — автозаполненные поля экранов 1–2, которые Мария проверяет и правит перед тем, как двигаться дальше (не слепое доверие распознаванию — тот же принцип human-in-the-loop, что и для AI-формулировок).

**Экран 4 — Генерация и результат.** Кнопка «собрать комплект»; если данных не хватает — список, что дозаполнить, по документам. После успешной генерации — список готовых файлов .docx с возможностью скачать каждый или всё архивом.

**Технологию (какой конкретно инструмент/фреймворк поднять под эти экраны) я не выбираю сама** — это инженерное решение (домен MAIN_ENGINEER, не Chief of Staff), и любой мой конкретный вариант (например, «сделай на Х») был бы непроверенным предположением о том, что быстрее всего поднять в вашем техническом контуре. В ТЗ Инженеру — прямая задача: предложить 2–3 варианта реализации экранов 1–4 (например: простое локальное веб-приложение / готовый no-code конструктор форм / другое), с оценкой по двум критериям, понятным не-технически: (а) сколько времени до рабочей версии, (б) что нужно, чтобы Мария сама вносила правки в шаблоны и логику в будущем без Инженера.

## 7. Защита от рисков

- **Версионирование шаблонов + привязка комплекта к версии** — устраняет проблему разрозненных шаблонов на уровне архитектуры.
- **Обязательные поля блокируют генерацию** с пустыми юридически значимыми данными (паспортные данные, кадастровый номер, цена, доли участников).
- **Cross-document consistency check** — все документы комплекта из одного источника данных, расхождения исключены по конструкции.
- **Human-in-the-loop перед подписанием** — система готовит черновики в .docx, финальную юридическую проверку делает человек. Особенно важно с динамическим комплектом: список согласий/актов зависит от `consent_flags`, которые вводит человек — ошибка ввода флага должна быть видна человеку до подписания, не только автоматике.
- **Персональные данные (паспорт, ФИО, контакты) — ПРЕДПОЛАГАЮ**, что для Phase 1 (один пользователь) достаточно базовой защиты доступа; при Phase 3 (SaaS) — отдельная проверка на 152-ФЗ, **[УТОЧНИТЬ]** у юриста, не входит в это ТЗ.
- **Фото паспортов (Phase 1.1) поднимают уровень риска персональных данных выше, чем текстовые поля** — если распознавание идёт через внешний AI-сервис (например, Claude Vision), сам скан паспорта покидает компьютер Марии и уходит во внешний сервис, а не только его текстовое содержимое. Локальный OCR (распознавание текста на фото без отправки куда-либо) этого риска не создаёт, но может быть менее точным. Открытый вопрос, решение не принято — раздел 9.
- **AI-сформулированные особые условия (Phase 1.2) не встраиваются в файл без подтверждения человеком** — см. раздел 5.1. Это самый непроверенный текст во всём комплекте документов, риск ошибки здесь выше, чем в готовых шаблонах.

## 8. Фазы (Phase 1 — это ТЗ, Phase 2/3 — референс на будущее)

**Phase 1 (сейчас, срочно):** один пользователь (Мария) → веб-форма (разделы 4–6) → Генератор → набор .docx на выходе. Хранение шаблонов — файлы с плейсхолдерами. Без сложной авторизации, но модель данных с полем `agent_id` и списком `Participants` с первого дня — чтобы Phase 2 не требовала переделки структуры.

**Phase 2 (при росте в агентство, не сейчас):** несколько сотрудников, роли, БД вместо файлов, интерфейс управления шаблонами с approve-процессом.

**Phase 3 (продукт на монетизацию, не сейчас):** мультитенантность, биллинг, кастомизация шаблонов под юрлицо клиента, полноценное соответствие 152-ФЗ.

**Явно вне Phase 1:** авторизация нескольких пользователей, БД, мультитенантность, биллинг.

**Phase 1.1 (добавлено 2026-08-21) — загрузка документов и автозаполнение.** Загрузка фото/скана паспорта каждого участника и выписки ЕГРН → распознавание (OCR или Claude Vision, решение открыто — раздел 9) → автозаполнение полей экранов 1–2 → Мария проверяет и правит перед продолжением.

**Phase 1.2 (добавлено 2026-08-21) — особые условия.** Библиотека типовых переключателей (снипет-шаблоны в том же Template Registry) + свободный текст → AI формулирует пункт → подтверждение человеком перед вставкой в файл. Подробности — раздел 5.1.

**Замечание по объёму (мentor reflex):** Phase 1.1 и 1.2 расширяют то, что было названо «срочным инструментом под текущую сделку», до полноценного продукта за два сообщения. Не блокирует работу, но стоит держать в уме при оценке сроков от Инженера.

## 9. Открытые вопросы

- Точный список оснований для `consent_flags` и когда согласие обязательно по закону — **[УТОЧНИТЬ]** у юриста.
- Акт приёма-передачи — один на сделку или на каждого участника — **[УТОЧНИТЬ]** у юриста / по практике агентства.
- Конкретный технологический вариант UI и шаблонизатора .docx — решает Инженер (раздел 6).
- **Локальный OCR или Claude Vision для распознавания фото паспортов/ЕГРН (Phase 1.1) — открыто, ждёт решения владельца.** Точнее vs данные покидают компьютер, раздел 7.
- **Обязательное подтверждение AI-сформулированных особых условий перед вставкой в файл (раздел 5.1) — предложено ассистентом 2026-08-21, ждёт подтверждения владельца**, не Locked.

## 10. Что НЕ делать

Мультитенантность и биллинг сейчас — Phase 3. Своя БД в Phase 1 — избыточно для одного пользователя. Автоматическое подписание без человека в цикле — риск не снят статистикой. Переписывание содержания юридических шаблонов или самостоятельное определение правил согласий силами Инженера/ассистента — решение Марии/юриста, не инженерная или ассистентская задача.

## 12а. Тестирование прототипа Phase 1 (2026-08-21)

Инженер поднял рабочий прототип (Flask, `http://127.0.0.1:5001`). Ассистент прогнал полный сценарий (создание сделки → 2 участника, один в браке → условия → генерация) напрямую через HTTP-запросы (без браузера — расширение не подключено).

**Работает верно:** все 4 экрана и переходы между ними; динамический состав комплекта — на тестовой сделке система верно насчитала 5 документов (2 комиссии + основной договор + акт + согласие супруга), совпадает с разделом 5; реестр шаблонов верно блокирует генерацию файлов, когда активного шаблона нет, и называет, какого именно не хватает.

**Найден дефект (нужно чинить до реального использования):** кириллица в введённых данных ломается при сохранении/отображении — «Иванов Иван Иванович» показывается как `%C8%E2%E0%ED%EE%E2...`. Это не только косметика: значение `deal_type` («аренда») ломается тем же образом и перестаёт совпадать с ключом реестра шаблонов — то есть даже при загруженных шаблонах система рискует не находить нужный для сделок, где тип сделки записан кириллицей (а он всегда так записан).

**Замечание по безопасности:** на сервере включён debug-режим Werkzeug — при ошибке показывается интерактивная консоль Python. Риска пока нет (сервер слушает только 127.0.0.1), но выключить до того, как через инструмент пойдут реальные данные клиентов.
