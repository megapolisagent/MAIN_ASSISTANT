# Business Gap Mapping
## Карта дефицитов существующего бизнеса

> Не для бизнеса «с нуля» — для этого есть `business-teardown` (`AI Business Producer`), он уже строит стартовый «хребет» функций (клиент/отличие/активы/веха → фазы). Этот скилл — для уже стоящего или частично стоящего бизнеса: проверяет каждый узел на дефицит, а не проектирует структуру заново.

## Принцип

Пять слоёв ниже — не изобретены заново, каждый слой — отдельная, десятилетиями используемая практика (карта организации Rummler-Brache, SIPOC, swimlane-диаграмма, проверка документации по ISO 9001, brand/touchpoint-аудит), объединённые в одну цепочку по узкому исследованию Researcher (`AI Intelligence/knowledge/evidence/2026-08-24-company-gap-mapping-methodology.md`). Честно: готовой методики, которая делает всю цепочку целиком, в природе не найдено — сама цепочка это синтез, каждое звено в ней — проверенный факт.

## Метод

### 1. Не строй структуру с нуля — сначала проверь, есть ли она уже

Прежде чем раскладывать функции заново, проверь `AI Business Producer/knowledge/businesses/*.md` (read-only, `HOME.md`, «Границы») — «хребет» уже мог быть построен `business-teardown`. Если файл для этого бизнеса есть — бери функциональную структуру и фазы оттуда как готовый слой 1, не придумывай заново. Нет файла — строй список функций сама: **Relationship Map** (какие функции есть, что каждая передаёт следующей) + для маленького бизнеса-под-владельцем стартовый чек-лист EMyth (Лидерство / Маркетинг / Финансы / Управление + Выполнение обязательств перед клиентом / Конвертация лидов / Генерация лидов) как отправная точка, не исчерпывающий список.

Запиши, с чем работаешь (весь бизнес или одно направление), в `workspace/<дата>-gap-map-<слаг>.md`, прежде чем идти дальше — не редактируй этот файл впоследствии, уточнения дописывай под ним отдельно с датой.

### 2. По каждой функции — клиент до деталей (SIPOC)

Прежде чем расписывать шаги внутри функции, назови: кто отдаёт вход этой функции (Поставщик), что на входе, 4-7 крупных шагов процесса, что на выходе, и — обязательно — **кто получатель** (Клиент), включая внутреннего: одна функция может быть клиентом другой (например, «сделка» — клиент «маркетинга», не только конечный покупатель). Пропуск этого шага — частая причина, по которой разбор через три месяца оказывается «мы вообще не то расписывали».

### 3. Каждый ключевой процесс — как дорожки (swimlane)

Разложи процесс так, как он реально идёт (не как должен идти в теории), одна дорожка — один исполнитель/роль. Правило чтения карты:

- **Пустая клетка на шаге** — нет исполнителя, никто не взял на себя этот шаг → дефицит «нет исполнителя/роли».
- **Несколько дорожек одновременно активны на одном шаге без ясного владельца** — отдельный, не тот же самый тип дефицита: спорная ответственность/дублирование, не «никого нет» (найдено исследованием как второй тип поверх исходной тройки — стоит не смешивать с первым).
- **Все дорожки молчат на каком-то шаге, хотя процесс должен продолжаться** — обрыв процесса.

**Проверка источника перед тем, как читать карту.** Прежде чем применять три правила выше — спроси: то, на чём ты строишь swimlane (обычно шаг 1 — `business-teardown` или похожий разбор), описывает *реально наблюдаемый* процесс, или *задуманную/плановую* структуру («специалист по запросу», роль на бумаге, ещё не нанятый человек)? Для бизнеса на ранней стадии (соло-фаундер, до операционки) источник почти всегда плановый, не наблюдённый — тогда пустая клетка ещё не факт «дефицит», это может быть просто нормальная стадия «пока не наняли». В этом случае: понижай уверенность записи и уходи в «недостаточно данных» (шаг 6, поле «Условие») быстрее, чем достраиваешь процесс вокруг колонки-намерения — не путай запланированную роль с подтверждённой.

### 4. По каждому шагу — есть ли документ/регламент

Проверяй не «существует ли вообще документация», а точечно по шагу: есть ли документированная информация, достаточная, чтобы быть уверенной, что шаг выполняется предсказуемо, не по памяти конкретного человека? Используй уже построенную swimlane-карту — не собирай отдельный список документов заново.

### 5. Клиентские шаги — сверка с брендом (только там, где клиент реально соприкасается)

На шагах, где клиент касается бизнеса (сайт, коммерческое предложение, счёт, онбординг, соцсети, подпись в письме) — проверь: то же ли позиционирование/голос/ценности, что заявлены (`PROFILE.md`, бренд-материалы Марии), или расходится. Список точек контакта — уже побочный продукт шага 3 (клиентские дорожки), не строится заново.

### 6. Один дефицит — фиксированный формат записи

По одному найденному дефициту:

| Поле | Смысл |
|---|---|
| **Узел** | Функция → Процесс → Шаг (координата на карте из шагов 1-3) |
| **Тип** | нет исполнителя/роли · нет документа/регламента · обрыв процесса · спорная ответственность (шаг 3) |
| **Условие** | что есть сейчас, факт |
| **Критерий** | что должно быть (источник критерия зависит от типа: для роли — шаг 3, для документа — шаг 4, для обрыва — шаг 3) |
| **Причина** | корневая — спрашивай «почему» пока ответ не станет системным, не поверхностным |
| **Эффект** | конкретное «и что тогда» — реальный вред клиенту/бизнесу, не абстракция |
| **Рекомендация** | твоё предложение (в отличие от Researcher — ты рекомендуешь, `HOME.md`, «Принципы работы с Марией») |

### 7. Ранжирование дефицитов по срочности

Для каждого дефицита — три оценки по шкале 1-3 (не 1-10, это разбор одного владельца, не команда инженеров): **Impact** (насколько плохо, если не исправить) × **Frequency** (как часто узел вообще задействуется — на каждой сделке или раз в год) × **Silence** (узнает ли Мария сама, или только когда клиент уже ушёл/пожаловался). Итог 1-27, сортировка по убыванию. Silence — сознательно оставлен третьим множителем, не упрощается до Impact×Frequency: тихий дефицит (клиент тихо перестаёт рекомендовать) при равной тяжести и частоте опаснее громкого (клиент, который хотя бы пожаловался).

### 8. Сохрани и покажи

Сохрани карту дефицитов в `knowledge/businesses/<слаг>-gap-map.md` (тот же паттерн, что `AI Business Producer`, отдельный файл, не пересекается с её `business-teardown`-файлами). Марии — по No-Noise Policy (`HOME.md`) — только готовая таблица дефицитов, отсортированная по срочности, не сырой разбор по шагам 1-5.

## Честные пробелы (не достроено предположением)

- Ни одной готовой методики, которая делает всю цепочку 1-5 целиком, не найдено — цепочка целиком является синтезом этого скилла, не готовым внешним стандартом. Каждое звено по отдельности — подтверждённая практика.
- Ни одного примера применения этой цепочки именно к брокериджу недвижимости не найдено — общая бизнес-практика, не отраслевая проверка.
- Открыто владельцем: является ли MAIN_ASSISTANT переименованием записи «AI Business Producer» в реестре агентов, или это разные агенты с разными задачами — не решено здесь, не мой вопрос как Skill.
