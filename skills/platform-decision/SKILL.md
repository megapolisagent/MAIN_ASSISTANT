# Platform Decision
## Как принять решение, какой механизм платформы использовать

> Задача Lead Agent: не выполнять задачу самому — найти, что уже умеет платформа. Этот документ отвечает на вопрос «почему именно этот механизм сейчас», а не «что умеет каждый инструмент». Общий принцип (потребность отдельно от инструмента, обязательный Platform Decision Record) — `instructions/capability-resolver.md`, Foundation-канон. Здесь — его конкретная реализация под фактический набор возможностей MAIN_ASSISTANT.

---

## Архитектурная схема

```
Claude Code instance        ← Lead Agent (runtime, оркестратор)
        ▲
        │ читает, использует
        │
MAIN_ASSISTANT/             ← конфигурация + знание (не агент, не оркестратор)
  ├── HOME.md               (Decision Policy)
  ├── PROFILE.md            (контекст пользователя)
  ├── skills/platform-decision/SKILL.md  (capability map)
  └── Memory                (накопленное знание между сессиями)
```

**Ключевое разграничение:** MAIN_ASSISTANT — это то, чем сконфигурирован Lead Agent, а не сам Lead Agent. Platform = execution. System = knowledge.

---

## Дерево решений

Пройти все вопросы. Ответ ДА добавляет механизм в план — не останавливает проверку.

```
Задача получена
│
├─ Нужна информация?
│   ├─ Она уже есть в системе? ──────────────────► Memory / Project Knowledge / DECISIONS.md
│   └─ Нужен актуальный факт из внешнего мира? ──► Web
│
├─ Нужен доступ к внешнему сервису? ────────────────► MCP
│   (GitHub, почта, БД, API — то, что Claude не умеет сам)
│
├─ Нужна работа с файлами / кодом / bash? ──────────► Claude Code
│
├─ Это повторяемая процедура? ──────────────────────► Skill
│   (будет вызываться регулярно — не один раз)
│
├─ Нужен параллельный независимый исполнитель? ─────► Sub-agent
│
├─ Нужен план перед сложным действием? ─────────────► Planning
│
└─ Это долгоживущая роль или продукт? ──────────────► Claude Project
    (специализированный агент, не разовый разговор)
│
▼
Что из платформы НЕ решает задачу?
└─ Только это → Engineering Hand-off
```

## Capability Resolver

> Lead Agent (Claude Code instance) определяет когнитивную потребность в THINK — Resolver выполняет операционный lookup: класс потребности → capability. Resolver не «думает» — это маппинг. Когнитивная работа происходит в THINK (Need Discovery). Resolver механический.
> Decision Policy `HOME.md` задаёт правила — Lead Agent исполняет. Lead Agent не должен знать, что существует WebSearch, MCP Calendar и т.д. — только что возникла потребность класса VERIFY или EXTERNAL CONTEXT.

### Маппинг классов потребностей в capabilities

| Класс (Need Discovery) | Capabilities |
|---|---|
| **REMEMBER** | Memory / DECISIONS.md / MAIN_ASSISTANT_STATE.md / filesystem |
| **VERIFY** | WebSearch (текущий default) |
| **EXPLORE** | Sub-agents / параллельный поиск |
| **EXTERNAL CONTEXT** | MCP (Calendar, Gmail, и т.д.) |

**Ownership:** MAIN_ENGINEER. При появлении нового capability (MCP, Skill, плагин) — MAIN_ENGINEER обновляет этот маппинг и раздел Available Platform Capabilities ниже.

**При отсутствии capability для класса:**
```
Need class: [REMEMBER / VERIFY / EXPLORE / EXTERNAL CONTEXT]
Resolution: не найдена
Signal: [одна строка — чего именно не хватает]
```
THINK принимает ограничение, переходит в JUDGE с маркером НЕ ЗНАЮ. Маркер становится входом для Engineering Hand-off.

## Available Platform Capabilities

> Ownership: MAIN_ENGINEER. Обновлять при изменениях конфигурации. Последняя верификация: 2026-07-17.

### Обязательная комплектация — без этого система не работает

| Capability | Класс | Почему обязательна |
|---|---|---|
| Filesystem (read-only) — DECISIONS.md, MAIN_ASSISTANT_STATE.md, MAIN_ENGINEER/, AI_Projects/ | REMEMBER | Основа роли Chief of Staff: знать контекст до начала разговора |
| Auto-memory (`~/.claude/projects/MAIN-ASSISTANT/memory/`) | REMEMBER | Накопление знания о Марии между сессиями — **не наша система**, см. `instructions/memory-rules.md` |
| WebSearch | VERIFY | Рекомендации по платформам и рынку требуют актуальных данных |

### Опциональные — подключаются по задаче

| Capability | Класс | Когда подключать |
|---|---|---|
| Gmail MCP | EXTERNAL CONTEXT | Задача касается переписки Марии |
| Google Calendar MCP | EXTERNAL CONTEXT | Задачи планирования и расписания |
| Google Drive MCP | EXTERNAL CONTEXT | Работа с документами |
| Sub-agents (Agent tool) | EXPLORE | Широкий параллельный поиск, изоляция объёмных результатов |

### Planned Automations — сейчас существуют как протоколы, не Skills

| Процесс | Текущий статус | Когда станет Skill |
|---|---|---|
| Engineering Hand-off | Протокол в `HOME.md` | После первого реального повторного использования |
| Agent Specification | Протокол в `HOME.md` | После первого реального повторного использования |
| Session Capture | Протокол в `HOME.md` | После первого реального повторного использования |

**Не входит в комплектацию MAIN_ASSISTANT:** Tavily, Exa, Context7, Sequential Thinking, Playwright — это окружение MAIN_ENGINEER для AI_Projects/, не для Chief of Staff.

## Карточки механизмов

### Memory

**Признаки выбора:** нужно вспомнить что-то из прошлых сессий; нужно сохранить что-то для будущих сессий.

**Использовать когда:** информация нужна в нескольких сессиях подряд; это факт о Марии, подтверждённый принцип работы, контекст активного проекта; наблюдение достигло уровня L1+ и имеет явную ценность для будущего.

**НЕ использовать когда:** информация относится только к текущей сессии; это черновик, гипотеза или временное состояние задачи; наблюдение L0 — записать позже, если повторится.

**Типичные ошибки:** писать гипотезы как факты (без маркера уровня); использовать неверный тип; не проверять актуальность; писать после каждого разговора без разбора ценности.

**Комбинации:** Memory + Projects (агент знает историю), Memory + Web (исследование запоминается), Memory + Skills (процедура применяется с контекстом).

### Project Knowledge / DECISIONS.md

**Использовать когда:** есть файлы с контекстом проекта, методикой; Мария уже принимала решение по этой теме; нужен большой объём контента (до 200K токенов активно, ~10x через RAG).

**НЕ использовать когда:** нужно точное word-for-word извлечение из документа (Knowledge — semantic search, не exact retrieval); документ не структурирован.

**Типичные ошибки:** считать что «загрузил документ → Claude знает его дословно»; загружать несвязанный контент.

**Комбинации:** Project Knowledge + Memory + System Prompt = специализированный агент с долгой памятью.

### Web

**Использовать когда:** возможности Claude/GPT/MCP/Skills/API и других платформ; версии продуктов и их ограничения; рыночные данные, цены, тарифы; новости, релизы, изменения.

**НЕ использовать когда:** ответ есть в `DECISIONS.md` или Project Knowledge; задача — reasoning, архитектурный анализ, инженерное решение; нужно мнение, а не факт.

**Типичные ошибки:** отвечать на вопросы о платформе из training knowledge без Web; использовать Web там, где нужен reasoning.

**Комбинации:** Web + Memory, Web + Sub-agents.

### MCP серверы

**Использовать когда:** нужно отправить письмо (Gmail MCP); доступ к GitHub issues/PR; запросы к БД; внешний API, которого нет нативно.

**НЕ использовать когда:** Claude умеет это сам нативно; сервис нужен один раз; MCP подключён, но не используется >2 недель.

**Типичные ошибки:** подключать «на всякий случай» — каждый сервер = тысячи токенов overhead (4 сервера ≈ 7,000 токенов, 5+ ≈ 50,000+ токенов); не делать аудит подключённых серверов; Gmail MCP — 2,640 токенов за 7 инструментов, дорого без реальной задачи.

**Комбинации:** MCP + Skills, MCP + Memory.

### Skills

**Использовать когда:** процедура повторяется регулярно; нужно кодировать конкретный способ делать стандартную задачу; хочется вызывать процедуру через `/skill-name`.

**НЕ использовать когда:** процедура одноразовая; правило ещё нестабильно (L0-L1); уже есть 10+ Skills — сначала ревизия.

**Типичные ошибки:** описывать протоколы текстом в `HOME.md` вместо Skills; накапливать Skills без ревизии; создавать Skill для одноразовой задачи.

**Комбинации:** Skills + Projects, Skills + MCP.

### Sub-agents

**Использовать когда:** широкий поиск по filesystem/нескольким источникам; параллельный research; изолированные технические подзадачи; нужно защитить главный контекст от объёмных результатов.

**НЕ использовать когда:** задача требует единого контекста и постоянного уточнения; одноразовая простая задача; части задачи зависят друг от друга.

**Типичные ошибки:** запускать Sub-agent для задачи, требующей живого диалога; не разграничить write-операции.

**Комбинации:** Sub-agents + Web, Sub-agents + Planning.

### Planning (EnterPlanMode)

**Использовать когда:** перед сложной реализацией; перед Mode C Hand-off; когда масштаб изменений неизвестен.

**НЕ использовать когда:** простая однозначная задача; уже есть готовый план.

**Типичные ошибки:** пропускать Planning для многоэтапных задач.

### Claude Projects (claude.ai) — роль/агент

**Использовать когда:** нужен агент с постоянным System Prompt между сессиями; нужна Knowledge Base + Memory на уровне проекта; это роль (репетитор, коуч), не задача.

**НЕ использовать когда:** задача заканчивается за один разговор; нужен exact retrieval из документов; нужны bash/file/Claude Code tools (Projects их не имеет).

**Типичные ошибки:** создавать Project для разовой задачи; загружать неструктурированные PDF; ожидать дословного воспроизведения документа.

**Важно:** Voice в Projects = только voice-to-text INPUT (18 языков, push-to-talk). Native voice OUTPUT отсутствует.

### Claude Code tools (файлы/bash/code)

**Использовать когда:** читать/редактировать/создавать файлы; запускать bash-команды, тесты, скрипты; навигация по codebase; всё, что требует реальных действий в системе.

**НЕ использовать когда:** задача — мышление, анализ, разговор.

### Hooks / Cron

**Hooks** — реактивные (session end → capture, tool call → log). **Cron** — проактивные (ежемесячная ревизия STATE.md, напоминание о сроках ревизии гипотез).

**Сейчас не используются, но должны быть:** Hook — Session Capture автоматически при завершении сессии; Cron — ревизия гипотезы «знание→действие» до 2026-09-16.

## Каскад проверки перед Engineering Hand-off

```
1. Memory / Project Knowledge / DECISIONS.md — есть ли уже зафиксированный ответ?
2. Web — нужен актуальный факт из внешнего мира?
3. Skills — есть ли готовая процедура для этой задачи?
4. MCP — нужен доступ к внешнему сервису? (проверить стоимость токенов)
5. Sub-agent — задача делится на независимые параллельные части?
6. Planning — нужен структурированный план перед действием?
7. Claude Code — нужна работа с файлами, кодом, bash?
8. Claude Project — это долгоживущая роль, не разовый разговор?
9. Финальный вопрос — чего именно не хватает платформе? Это и есть содержание Engineering Hand-off.
```

## Platform Decision — выходной артефакт

После каскада сформировать и показать:

```
Platform Decision

Использовать:
✓ [механизм] — [одна строка: зачем]

Не использовать:
✗ [механизм] — [одна строка: почему не нужен]

Недостающая возможность платформы:
[что именно не умеет] / "отсутствует"

Вывод:
Engineering требуется / не требуется
[если требуется — одна строка: что именно]
```

## Platform Decision Record — обязательная запись

**Когда обязательна:** перед Engineering Hand-off, при запуске нового агента или проекта, при любом архитектурном решении. Формат — `instructions/capability-resolver.md` (Foundation-канон).

**Хранение:** не сохраняется отдельно — остаётся в сообщении как рабочий артефакт сессии. Если по его результатам принимается долгоживущее архитектурное решение — в `DECISIONS.md` переносится только итоговое решение, не весь процесс выбора механизмов.
